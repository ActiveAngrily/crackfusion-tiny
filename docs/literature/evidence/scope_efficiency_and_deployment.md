# Efficiency and deployment evidence

**Scope.** This note covers compute and deployment evidence relevant to binary crack-image classification, with closest crack segmentation/deployment studies included only as adjacent context. Classification throughput must not be compared directly with segmentation throughput: segmentation predicts dense masks, often at larger resolutions and with decoder/post-processing cost. The review is a targeted survey, not a claim to have read every paper in the field.

## Repository implications

The proposed classifier receives 224×224 RGB images and has 284,337 trainable parameters in the implemented graph ([`src/crackfusion_tiny.py`](../../../notebooks/03_crackfusion_train.ipynb)). The operational baseline is pretrained `timm` MobileViT-XS with its task head replaced; its exact parameter count, transform and library/checkpoint revision must be measured in the run. The original ImageNet-1K model is reported as about 2.3M parameters at 256×256; that number is not the one-logit crack classifier's exact count. Current validation outputs are development-split accuracy artifacts, not deployment measurements. The codebase audit identifies missing controlled efficiency measurements and says the existing optional timing loop (5 warm-ups, 20 timed batch-1 iterations) is too short for research reporting. No claim that the 0.284M model is faster follows from its parameter count.

### MobileViT compute references and accounting cautions

MobileViT-XS values vary by implementation and input. The original paper/model card commonly gives ~2.3M parameters and 256px input. Later comparison tables can list different FLOPs: for example, an ICLR 2025 paper's model table lists MobileViT-XS at 256 input, 2.3M parameters, 0.986G FLOPs and 74.8 top-1; another mobile comparison describes MobileViT-XS as 0.9G at 256px. This reflects differences in implementation and operation-count convention, not evidence of a different task result. [ICLR 2025 paper](https://openaccess.thecvf.com/content/ICCV2025/papers/Zeng_An_Efficient_Hybrid_Vision_Transformer_for_TinyML_Applications_ICCV_2025_paper.pdf) · [ICLR 2022 paper](https://openreview.net/forum?id=vh-0sUt8HlG)

FLOPs/MACs are tool- and convention-dependent (one multiply-accumulate may be counted as one or two operations); parameter count is not file size; theoretical FLOPs are not latency; GPU FPS at batch >1 is not single-image phone latency. For the project's binary head, the original 1000-way classifier is replaced, so both parameter count and checkpoint bytes should be reported from the instantiated task model. List the counting tool/version, input tensor shape, FLOPs vs MACs convention and included operators.

## Synthesis and implications for this paper

1. **A size claim is not a speed claim.** CrackFusion-Tiny's 0.284M parameters is a measured graph count and suggests a compact model, but it does not establish low latency, low energy, or deployability. Transformer attention, memory movement, operator support, and preprocessing can dominate even when parameter counts are small.
2. **Separate two comparisons.** (a) Controlled model efficiency on one fixed platform: same 224×224 input, batch 1, framework/backend, precision, warm-up and timing boundary for all classifiers. (b) Practical transfer baseline: MobileViT-XS uses its own documented checkpoint preprocessing and may use 256px; label differences instead of implying architecture-only causality.
3. **Do not promise edge deployment before measuring it.** Current code supports a design-level compactness statement only. An actual phone/edge claim needs a named device and exported artifact/runtime. For a later deployment extension, benchmark one CPU phone/SBC and optionally a mobile accelerator, with supported FP32/FP16/INT8 paths measured separately.
4. **Do not pool platform-specific FPS.** 2026 works report compelling phone/UAV numbers, but headline FPS can omit input size, batch, preprocessing, model loading or quantization. Keep them contextual until methods are fully verified.
5. **Classification and segmentation live on different workload axes.** Report dense crack segmentation studies in an adjacent-work paragraph, never in the classifier speed leaderboard.

## Actionable efficiency reporting checklist

For every classifier row, record:

- exact model graph and task head; trainable and total parameter counts; source/checkpoint URL and revision; pretrained dataset/initialization; exact task checkpoint file size;
- input resolution, channels, crop/resize/normalization, and whether preprocessing is included in the timing;
- theoretical MACs or FLOPs at that resolution, counting convention, tool and version;
- device model, CPU/GPU/NPU, OS, memory, runtime/framework and version, delegate/compiler, thread count, and power/performance mode;
- precision and quantization calibration (FP32/FP16/INT8), batch size, warm-up count, timed repetitions, synchronization method, and summary statistic (median plus spread or p95);
- single-image latency separately from batched throughput; model load/start-up excluded or separately shown; preprocessing and postprocessing timing separated, plus end-to-end total;
- peak RAM/accelerator memory, deployed artifact/flash bytes, and energy per inference only when measured with stated instrument/method and repeated-run conditions;
- identical frozen evaluation samples and predictions/metric definitions when linking compute to quality; report recall/F1/AP alongside efficiency, not accuracy alone;
- source-photo-separated split and cross-surface results before making generalization claims; distinguish repeated seeds on one fixed split from independent test domains.

Minimal planned benchmark for this study: run CrackFusion-Tiny and the binary MobileViT-XS task model on the same frozen test examples and 224×224 input on one named device, batch 1, eval mode, FP32. Warm up at least 50 runs, time at least 500 runs with accelerator synchronization, report median and p95, and separately report preprocessing, forward pass and end-to-end latency. Record parameter count and serialized checkpoint bytes; calculate MAC/FLOPs for each at the stated resolution. This is a proposed repeatable protocol, not an executed result. If 256px is retained for MobileViT due to its official transform, publish that as a separate practical-baseline measurement rather than the controlled 224px comparison.
